Workflow: Governance Authoring & Architecture Decision

📐 Enterprise / Solution Architect

Full cycle from identifying a governance need through authoring directives/norms, evaluating impact, and recording an ADR.

1

Identify Governance Gap

Architect reviews the Dashboard and spots a low compliance score or a new structure lacking governance coverage.

📄 Screen: Dashboard
┌──────────────────────────────────┐ │ Dashboard Alerts │ ├──────────────────────────────────┤ │ ⚠ AuditService: 67% compliance │ │ 2 norms failing (NIS2) │ │ [Investigate →] │ │ │ │ 📋 PaymentService (PROPOSED) │ │ No directives attached yet │ │ [Author Governance →] │ └──────────────────────────────────┘
2

Explore Current State

Navigate to Structure Explorer to understand the structure's current norms, ascriptions, and relationships before authoring new governance.

📄 Screen: Structure Explorer
┌──────────────────────────────────┐ │ PaymentService — Detail View │ ├──────────────────────────────────┤ │ State: PROPOSED │ Type: Service │ │ Archetype: ItSoftwareTechnology │ │ │ │ Mechanisms: │ │ • PaymentProcessing (Active) │ │ • FraudDetection (Draft) │ │ │ │ Interactions: │ │ • PaymentService ↔ UserDB │ │ • PaymentService ↔ APIGateway │ │ │ │ Current Norms: 0 │ │ Applicable Frameworks: NIS2, │ │ GDPR, PCI-DSS (not sourced) │ │ │ │ [Author Directive →] │ └──────────────────────────────────┘
3

Author Directive (Grammar Builder)

Open the Governance Authoring workspace. Use the grammar builder to construct a directive statement following DNA grammar.

📄 Screen: Governance Authoring
✦ Copilot Assist
"Based on NIS2 Art.21 §2(b) and the PaymentService archetype, I suggest:
PaymentService MUST ENSURE PCI-compliant transaction encryption and tokenization ON PaymentProcessing
Suggested 3 norms: payment_encryption, card_tokenization, transaction_audit_trail"
4

Define & Validate Norms

For each norm, define the CEL applicability and assertion expressions. The editor validates syntax in real-time and shows which structures will be affected.

📄 Screen: Governance Authoring (Norms tab)
┌──────────────────────────────────┐ │ Norm: payment_encryption │ ├──────────────────────────────────┤ │ Scope: PaymentProcessing │ │ Tolerance: STRICT │ │ │ │ ┌── Applicability (CEL) ──────┐ │ │ │ subject.type == │ │ │ │ "PaymentMechanism" │ │ │ └─────────────────────────────┘ │ │ │ │ ┌── Assertion (CEL) ─────────┐ │ │ │ subject.encryption.algo │ │ │ │ in ["AES-256", "RSA-4096"]│ │ │ │ && subject.encryption │ │ │ │ .atRest == true │ │ │ │ && subject.encryption │ │ │ │ .inTransit == true │ │ │ └─────────────────────────────┘ │ │ │ │ ✓ CEL Valid │ Impact: 2 structs │ └──────────────────────────────────┘
5

Review Impact Analysis

Before submitting, check the impact panel to see which structures the new directive and norms will affect, and whether any existing norms conflict.

📄 Screen: Governance Authoring (Impact tab)
Decision: Impact acceptable?
✓ Proceed — PaymentService and FraudDetection affected, no conflicts
✗ Revise — narrow scope to avoid impacting FraudDetection (still in DRAFT)
◆ Split — separate directive for FraudDetection with TOLERANT norms
6

Submit for Approval & Record ADR

Submit the directive + norms for lifecycle progression (DRAFT → PROPOSED). Optionally generate an Architecture Decision Record capturing the rationale.

✦ Copilot: Generate ADR
"Generate an ADR summarizing this governance decision?"
ADR-042: Payment Transaction Security Governance Status: Proposed Date: 2025-01-15 Context: PaymentService entering ACTIVE state without payment-specific security governance. NIS2 Art.21 §2(b) requires encryption for financial transactions. Decision: Author directive requiring PCI-compliant encryption and tokenization on PaymentProcessing. Three norms: payment_encryption (STRICT), card_tokenization (STRICT), transaction_audit_trail (TOLERANT). Consequences: - PaymentService and FraudDetection must comply - Existing APIGateway already compliant (no change) - Next: FraudDetection governance in sprint 23
7

Monitor the directive through the approval workflow. Reviewers approve (PROPOSED → APPROVED → ACTIVE) or request changes. The Dashboard reflects updated compliance scores in real-time.
